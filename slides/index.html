The Starting Point

AI writes code faster than we make decisions.

An AI agent can produce more code in an hour than a team can review in a day. It looks like velocity — until you touch it.

  • Every file leans on an unwritten assumption.
  • The agent has zero memory across sessions — only what is committed to the repo survives.
  • Decisions not written down are re-negotiated or hallucinated in every prompt.

The red card at the bottom is the unverified assumption you only notice when the house stands.

Pause here. An agent produces code faster than we make decisions. Without recorded decisions and executable specifications, you get a house of cards.

Phase 2 Hands-On · Executable Specification (BDD Guidelines v1.9.0)

Count Error Paths First. Specify Positive and Negative Controls.

Positive Path (Lilly leaves the pasture → Alert written)

Scenario: Alert when a horse leaves the pasture
  When the service receives a Pub/Sub push event
       on "/telemetry-push" for "Lilly":
    """
    {"device": "Lilly", "lon": 9.6116704, "lat": 53.2275266,
     "timestamp": "2026-02-25T14:00:00Z", "zone": "HomePasture"}
    """
  Then the Firestore collection "alerts" should eventually
       contain a record for "Lilly" within 10 seconds:
    | field | value              |
    | type  | GEOFENCE_VIOLATION |
    | zone  | HomePasture        |

Negative Control (Honey stays inside → No alert)

Scenario: No alert when a horse remains inside
  When the service receives a Pub/Sub push event
       on "/telemetry-push" for "Honey":
    """
    {"device": "Honey", "lon": 9.6113700, "lat": 53.2280821,
     "timestamp": "2026-02-25T14:05:00Z", "zone": "HomePasture"}
    """
  Then the Firestore collection "alerts" should not
       contain a record for "Honey" within 2 seconds

Without the negative control on the right, a service that writes an alert for every request would pass the left scenario!

Phase 3 Hands-On · The Specification Critic (Guidelines §14)

Each Register Audits the Others — Before Code Exists

bdd-critic · Markdown & Gherkin Only

The Six Verification Edges

  • 1 · Binding Set: Do ADR/LIM indexes and statuses agree?
  • 2 · Record ↔ Record: Conflicting ports, schemas, or rules across ADRs?
  • 3 · Feature ↔ Feature: Identical payloads and coordinates across MI1–MI4?
  • 4 · ADR ↔ Feature & Error Paths: Every decided rule has a scenario; every scenario cites an ADR (# Source:).
  • 5 · LIM ↔ Both: Every deliberate V1 shortcut is backed by a LIM.
  • 6 · Scenario Honesty: Can every Then fail? Are boundary cases covered?
Why This Works

1 : 5.5 Specification Compactness

In source code, architectural reasons don't exist at all, and expectations are buried across mocks and fixtures.

In Markdown + Gherkin, every line is a claim. The entire specification of a service fits into one context window so an independent Critic Agent can cross-examine every claim at once.

Real-world proof: On our alerting Terraform module (30 ADRs, 11 LIMs, 7 features), bdd-critic found 24 defects — 3 blocking — without opening a single line of code.

Phase 4 Hands-On · Black-Box Steps & Test Honesty (§13 Spec-Audit)

Language-Neutral Seams & Independent Channels

ADR-0004 · 100% Language-Neutral

Black-Box Contracts

  • MI1 CLI: ./bin/geofence-lib-test (stdin JSON → stdout JSON {"is_inside": bool}).
  • MI2 Service: ./bin/geofence-processor (env vars PORT, FIRESTORE_EMULATOR_HOST, PROJECT_ID).
  • MI3 Container: Dockerfile → equiguard/geofence-processor:test.
  • MI4 Cloud: Terraform outputs + real Pub/Sub & Firestore.
Guidelines §13 · Step Honesty Audit

Three Rules Against Cheating LLMs

  • 1 · Independent Channel (§13.2): Never trust HTTP 200 alone! Read the alerts collection directly from Firestore.
  • 2 · Value Provenance: Every expected value in Then comes from Gherkin, never computed in Python.
  • 3 · Data Symmetry: Steps are dumb plumbing — zero hidden business fields or repairs.

What to Take Home

  • Decide before you build: ADRs (Why) + LIMs (Where Not) + Gherkin (What).
